What the model was shown

Notes from building a Mythic+ log coach on a 14B local model.

Date
2026-11
Status
stable
Reading
~8 min

At 22:40 into a +14 Kings’ Rest, Aka’ali the Conqueror hit my Protection Warrior for 693,808 with one melee swing. My health went from 89% to 23% in 2.4 seconds. I survived and forgot about it. I only know it happened because the combat log recorded it, and because I spent a few weeks building something to read that log back to me.

I used to paste these logs into ChatGPT. Warcraft Logs already gives me the charts. What I wanted was someone to talk me through the run and point at the places that deserved attention, and ChatGPT did that well. I am a backend engineer who has become curious about agents, and rebuilding a product I already use looked like a good way to learn how such a product works. None of this was meant to ship. It was practice.

A note on how the work was done. I did not write the code. One Claude session planned and reviewed, Claude Code wrote and ran everything on my machine, and I carried prompts and reports between them, made the decisions, and supplied the logs and the opinions of the person who was in the dungeon.

The setup

The model is qwen3:14b under Ollama, on an RTX 4070 Ti Super with 16 GB of memory and a 16,384-token context window. The log file from that evening holds three runs and tokenizes to 134 million tokens. The smallest single pull in it is 1.55 million. With thinking enabled the prompt has room for 10,240 tokens, so none of the 24 pulls fits, by a factor of at least 151.

So the model never reads the log. A parser writes every event to SQLite. A set of functions answers questions such as “what hit this player in the ten seconds before this moment” and “which of their own buffs had dropped”. The model gets those functions as tools.

I set one rule early: no hand-written class knowledge. Nothing in the code knows what a Protection Warrior is. Everything has to come from the log, so the same tools should work for a healer or a hunter.

Keeping the raw data away from the model felt strange to me at first. Then I looked again at what ChatGPT had done with my 180 MB file. Its write-up describes searching for health drops in two-second windows. That is code running over the file and a model commenting on the output. I had been using this design for months without seeing it.

The model knows what the tool shows it

For a baseline I gave the same run to ChatGPT and broke its answer into 36 checkable facts. 34 held up against the raw log, including aura timestamps that were correct to the millisecond. Its main finding was that Shield Block and Ignore Pain, my two short defensive buffs, were both down when Aka’ali’s big hit landed.

My agent, asked the same question, did not mention Shield Block. It reported that Shield Wall was “uncertain” and suggested I activate Darkflight, a racial sprint, earlier.

The data was in the database the whole time. The tool that reports a player’s buffs at a given moment left out anything used more often than every ten seconds, on the theory that those are rotation abilities. The two buffs that mattered never reached the model, and it built a story from what was left.

I added a second tool that shows everything around a moment, and wrote in the system prompt that questions like this should use it. On the next test run, all four buff questions still went to the old tool. My reading is that its one-line description sounded more like the question than my instruction did. Fixing the tools themselves moved that set from 5 of 10 correct to 8 of 10. A later attempt to steer through the system prompt, by describing an analysis method step by step, was followed in one run out of three and cost 21% more prompt tokens.

Code decides, the model tells

The open-ended request, “analyse my run”, stayed weak. The model would look at the single worst moment and stop there.

So I took the decisions away from it. A fixed pipeline now picks the hardest moments of a run. For each one it collects what hit me, which buffs were down, what I tried to cast and why it failed, and how much rage I had. It writes the result as a short list of candidate findings in plain sentences. The model receives that list and writes the coaching text.

Two details mattered more than I expected.

The first version of the digest packed each row as a positional array, and the model kept attaching numbers to the wrong event. Over three answers the average was four mislinked numbers, most of it from a single answer with nine. After the rows were rewritten with named keys, and the findings as sentences, the worst answer had two.

The second detail is where the pipeline found something ChatGPT had not. ChatGPT listed “Shield Block charges were exhausted” as one possible reason for the gap before the big hit. The log has a line for every failed key press. In the seconds after Shield Block dropped I pressed it four more times, and each press was rejected with “Not enough rage”. I had just spent that rage on Ignore Pain. The resource value and the cost of each ability are in the log as well, so the code can say this without knowing anything about warriors.

The measurements were wrong before the model was

Most of the time went into measurement, and most of the mistakes were there too.

The first held-out question set scored 0 of 10. Seven of the questions did not say which of the three runs in the file they were about, and the model usually picked the wrong one. With the dungeon name added, the same questions scored 5 of 10.

The measurement tools had three bugs of their own. One of them, in the check that looks for invented numbers, read “30 minutes 51 seconds” as two unrelated numbers. A check I added to catch invented ability names raised 47 flags on its first pass, and 31 of them were false alarms. Another check sent most answers back to the model for a second call. Response time roughly doubled on two runs, and I demoted that check to a silent log entry.

For a while everything was tuned on a single dungeon run. Eventually I set aside three runs that nothing had been tuned on, fixed the list of changes before any result was visible, and ran the old and new versions side by side. The changes made the model stick closer to the findings it was given. They did not increase how many important findings it covered. On the two tank runs coverage went down slightly.

The metric itself misled me once. “Important findings covered” read 3 or 4 out of 5 and looked healthy. Then I read the answers. One of them went through observation, hypothesis and advice three times over, each round a variation of the last. Most of the advice came down to “make sure you have enough rage”.

Same digest, five models

Near the end I had API credit to spend, so I ran the unchanged pipeline with four Claude models in place of the local one: 120 runs, just over $10 in total. The answers were graded blind, with model names removed and the order shuffled. The table covers the three runs that all five models share.

Model Key findings covered (of 15) Mislinked numbers per answer Citations that support the claim Cost per run
qwen3:14b (local) 10.5 1.61 66% none
Claude Haiku 5.5 11 0.22 97% $0.003
Claude Sonnet 5.5 11 0.06 99% $0.036
Claude Opus 5.5 11 0.00 over 99% $0.084
Claude Fable 5.1 11 0.11 97% $0.22

Every Claude model covered exactly 11 of the 15 findings I had marked as important. Eleven is also how many of those findings appear among the four candidates the code shows the model for each run. No model, at any price, recovered a finding that the pipeline had ranked below the top four.

What the larger models bought was accuracy in the telling. They almost never attached a number to the wrong event, and their citations pointed at the finding that supported the sentence.

Seeing the expensive model and the cheap one produce nearly the same thing made me feel the weight of the harness more than anything else in the project. It also leaves a question I cannot answer yet. The pipeline showed every model the same four findings, so I do not know whether a wider window would have let the stronger models pull apart.

One more observation from that experiment. The most capable model had the most “unsupported claims” in its free-form answers. There were 19 of them. By a rough classification, about 11 were correct statements about the game that were simply not in the digest. At least six were wrong, and three of those contradicted the digest. My grading rule counted all 19 as fabrication. That rule suited a small model that invents ability names. For a model that knows the game it is too coarse, because it cannot separate useful knowledge from a confident mistake, and I have no measure for that difference yet.

What this does not show

Five runs, three repeats each, all from one player’s logs.

The graders in the last experiment were Claude models as well. The reading was blind, but a model may recognise the style of its own family, and the local model was graded more harshly in that round than in an earlier one.

I have prepared a blind comparison to score myself and have not done it yet.

The coach is still shallow. It reports accurately on the four findings it is shown, and in the Kings’ Rest run those four cover only two moments of a thirty-minute key. ChatGPT’s original answer contained 34 correct facts, and the best answer from my pipeline reproduced six of them. A human tank coach would also ask whether I should have kept rage for Shield Block before a physical hit. That takes game knowledge, which my rules leave out on purpose.

The class-agnostic design has a visible cost outside tanking. On a run where I played a hunter and died twice, none of the four findings shown to the model was about the deaths, and no answer analysed them.

What I ask now

I used to think about AI products in terms of the model. Now the first thing I want to know is what the model is being shown, and who decided that. When a product digests a large file of mine in a few seconds, I assume there is a parser and a database behind it, possibly a cheaper model doing the summarising, and I am curious where the lines were drawn.

I also enjoyed something I had not planned for. The harness can stream the model’s reasoning to a terminal, and I spent more time than I needed to watching it work through a question:

Okay, so the user is asking how many times Urukzug used Spell Reflection in the Kings’ Rest run. Let me check the tools provided.

For someone who writes software and is curious about agents, I think it comes down to curiosity and practice. The field grows every day and the limits on what one person can build keep lifting, so the time is well spent building something you care about and can judge for yourself.
